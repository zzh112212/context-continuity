# 三文件工作法细则

来源：planning-with-files v3 精髓（去脚本化、跨 IDE 可移植版）。

## 核心模式

```
Context Window = RAM（易失、有限）
Filesystem     = Disk（持久、无限）
→ 重要的东西都写到磁盘
```

## 读写决策矩阵

| 情况 | 动作 | 原因 |
|---|---|---|
| 刚写完一个文件 | 不要读 | 内容还在上下文里 |
| 看了图片/PDF | 立刻写 findings.md | 多模态信息不转文字就会丢 |
| 浏览器/搜索返回数据 | 写 findings.md | 截图和页面不会持久 |
| 开始新阶段 | 读 task_plan.md | 上下文可能已陈旧，重新定位 |
| 出错时 | 读相关文件 | 修复需要当前真实状态 |
| 隔了一段时间恢复 | 读全部规划文件 | 恢复状态 |

## 2-Action 规则

每 2 次 view / browser / search 操作后，立刻把关键发现存为文字。这是防止多模态信息丢失的最低成本手段。网页内容只进 `findings.md`，绝不进 `task_plan.md`（后者会被反复读取注入，外部内容进入会放大注入风险）。

## 3-Strike 错误协议

```
第 1 次失败：诊断根因，针对性修复
第 2 次失败：换方法（换工具/换库/换路径），绝不原样重试
第 3 次失败：质疑假设，重新审视计划，考虑改 plan
3 次之后：升级给用户——说清试过什么、具体错误、请求指引
```

每次失败都记入 `task_plan.md` 的 Errors 表（错误、尝试次数、解决方式）。错误表的价值在于防止上下文压缩后"忘记已经失败过"。

## 5 问自检（饱和的定性判据）

连续回答不上来 = 上下文管理已失效，直接进入交接：

| 问题 | 答案来源 |
|---|---|
| 我在哪个阶段？ | task_plan.md 的 Current Phase |
| 我要去哪？ | 剩余阶段 |
| 目标是什么？ | plan 的 Goal |
| 我学到了什么？ | findings.md |
| 我做了什么？ | progress.md |
| 我下一步做什么？ | task_plan.md 的 Next Step |

能答上来但答案与文件冲突 → 以文件为准，立刻修正行为（决策漂移，饱和信号 S5）。

## 阶段推进规则

- 阶段状态只允许 `pending` / `in_progress` / `complete` 三个值。
- 状态变更时同步刷新 `## Next Step`，让它始终指向单一动作。
- 全部阶段完成后用户又提新需求 → 追加新阶段（Phase 6、7…），progress.md 记新会话，工作流照常。

## 并行任务

同一项目多个独立任务并行时，`.planning/` 下按任务建子目录：

```
.planning/
├── backend-refactor/
│   ├── task_plan.md
│   ├── findings.md
│   ├── progress.md
│   └── handoff.md
└── incident-investigation/
    └── ...
```

恢复时按任务名进入对应子目录。单任务项目直接用 `.planning/` 根，不必分子目录。

## 恢复时的只读原则

RESUME 状态下对 `.planning/` 只读不写，只创建缺失的文件（用模板内容填充骨架，不动已有内容）。冲突以文件记录为准，向用户指出差异而不是悄悄改写历史。
