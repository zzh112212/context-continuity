# 交接协议细则

## 交接简报逐节写法（templates/handoff.md 的填充指南）

接收方是**零上下文的新会话**。每一节都按"它只读这一个文件就要能接手"的标准写。

| 节 | 写法 | 常见错误 |
|---|---|---|
| 任务 | 一句祈使句说清要达成什么 | 写成对话流水账 |
| 上下文 | 为什么做这件事，什么背景 | 省略（接收方会重新发明需求） |
| 相关文件 | 路径 + 每个文件"是什么、为何重要" | 只给路径不给一句话说明 |
| 当前状态 | 哪些完成了、哪些能跑、哪些坏着 | 只写"做到一半" |
| 已试方案 | 方法 + 失败/放弃原因 | 只列方法不列原因（新会话会把失败的再试一遍） |
| 已定决策 | 决策 + 理由 | 省略理由（接收方会推翻它） |
| 验收标准 | 可勾选的清单 | 模糊（"做好了"） |
| 约束 | 必须保持/不能碰的东西 | 遗漏（接收方会破坏隐性约束） |
| 开放问题 | 待用户回答的问题，恢复时**置顶呈现** | 混在正文里 |

三个语义保全原则（继承自 paseo-handoff）：

- 调查型任务 → 明写 "只调查，不改文件"
- 修复型 → "实现修复"，重构型 → "重构而非重写"
- 任何任务模式词都要传递给接收方，防止语义漂移

## 饱和信号处置细则

信号定义见 SKILL.md 主表。处置分三档：

| 信号数 | 动作 |
|---|---|
| 1 条 | 静默警惕；把本阶段发现补写进 findings.md / progress.md（降低后续交接成本） |
| 2 条 | **主动交接**：告知用户"建议换窗口"，并立刻写 handoff.md（写完再建议，别先问后写——趁还记得） |
| 3+ 条或 S6（平台压缩） | 立即交接，无解释负担；此时连"解释为什么要交接"都在消耗所剩无几的上下文 |

**防频繁换窗**：只在阶段边界执行 2 条档动作（"一个阶段最多交接一次"）；阶段中间即使命中 2 条，先落盘发现、完成当前最小动作，到边界再交接。S6 例外：平台已在压缩，立即交接。

**防用户无感**：每个阶段完成时，在阶段汇报末尾附一句轻量状态（可选）：

```
（上下文状态：本会话已执行 N 次工具调用，预计还有充足/紧张余量）
```

不精确没关系，目的只是让用户对"该不该换窗口"有体感。

## 恢复对话示例（按此风格输出）

用户："resume"

正确输出：

```
📍 恢复任务「认证刷新重构」
❓ 未决问题：登出应吊销全部设备令牌还是仅当前设备？
✅ 已完成：刷新令牌轮换已实现并测试通过（阶段 2/5）
📂 关键文件：auth/refresh.ts（核心轮换逻辑）、auth/logout.ts（待改）
▶ 下一步：确认吊销范围后完成 auth/logout.ts
```

错误输出（对照）：

- ❌ 一上来就开始写代码（没先恢复状态）
- ❌ 复述整个 handoff.md 原文（用户要的是定位，不是文件转储）
- ❌ 开放问题藏在第三段（必须置顶）

## 空状态处理

- `.planning/` 存在但 handoff.md 缺失 → 从 task_plan.md + progress.md 尾部重建定位，并补写 handoff.md。
- `.planning/` 存在但全部为空模板 → "没有可恢复的任务状态。要开始新任务还是清掉这些模板？"
- 用户说 resume 但项目里没有任何 `.planning/` → 说明原因（"未找到 .planning/，本技能只恢复用文件保存过的任务"），若 MCP 可用则尝试 memory_sessions 恢复。
